## 一、B 提的两条（已实现）

### 1. `send_device_cmd` 的 schema 补 `task_no`（可选）

`app/agents/tools.py`：

```json
"properties": {
  "device_id": {"type": "string"},
  "action": {"type": "string"},
  "params": {"type": "object"},
  "task_no": {"type": "string", "description": "本轮要下发的任务号…不填则由平台自动带上"}
},
"required": ["device_id", "action", "params"]      // 仍然三个,老调用方不受影响
```

三条路落到同一张单，互不冲突：

1. 模型自己填（schema 现在允许了，system 里也给了本轮任务号）；
2. 模型没填 → `agents/base._with_executor_device` 用 ContextVar 里的本轮任务号补参；
3. 都没有 → 基座 `_pending_device_cmd` 认领 dispatched 且无 dispatch 轨迹的单。

### 2. 引擎起跑时 `set_current_run_id(run_id)`

`app/workflow/engine.py` 的 `_drive()`：进 `try` 前 `_bind_run_id(run_id)`，`finally` 里
`_release_run_id(token)`。基座 `core/run_context` 已有该 ContextVar，读不到时才退回
「唯一 running 的那条才认」的兜底 —— **并发跑两条就不会再记 NULL 了**。

实测 run #27/#29：`tasks.run_id=29`、`verifications.run_id=29` 均直接写入，不依赖兜底。

## 二、A 要求的全链路核对（顺带挖出四个真 bug）

### 事件链路（run #27，13 个节点，全部走完）

四类事件齐、顺序对：

| 类型 + 阶段 | 条数 | 说明 |
| --- | --- | --- |
| `run_status` / running | 1 | 第一个，`node_count` 齐 |
| `node_state` / started | 13 | 含 parallel 的 n3/n4/n5/n6 |
| `node_state` / finished | 13 | 每个 started 都有配对 |
| `run_status` / success | 1 | 最后一个，带 `rounds` / `duration_ms` |

`agent_message` 7 条，紧跟在对应 agent 节点的 finished 之后：
`scout → weather → soil → pest → decision → executor → verifier`。

### 挖出的 bug（都已修，都有测试）

#### bug 1：决策写「本轮决策**为**irrigate」被判成无需作业（run #26）

`DECISION_RE` 只认冒号。模型换个说法，`context.last_decision` 就提不出来 →
`n8 condition` 走 false → 「无需作业归档」。画布全绿、一滴水没浇，这是最难被抓到的失败。

修：
- 正则吃「：/:/为/是/直接跟」，`re.IGNORECASE`，提取后 `.lower()` 归一；
- 决策官**真调了 `create_task`** 就把 `last_decision` 钉成 `irrigate`（工具事实优先于措辞）。

#### bug 2：Self-Loop 只回验证官，物理世界一动不动（run #28）

`n11b.body_next` 原来是 `n11`（验证官）。三轮验证拿到的是同一批传感器数据，
达成率恒为 40.41%，`feedback_logs` 一行没有 —— 循环在画布上转了，茶垄没再浇一次。

修：
- `n11b.body_next` → `n9`：body 是「修正 → 再执行 → 再渗透 → 再验证」整段；
- 引擎新增 `_apply_correction`：把验证层已经算好的 `correction`
  （topup 19.9s / split / suspect_data）真的落成一张新单（`trigger=selfloop`、
  带 `device_id`、`priority=8`），并写 `context.feedbacks`；
- `wiring._persist_feedbacks` 落 `feedback_logs`（PRD 6.13 证据链）；
- `max_iterations` 改成**总轮次**口径（PRD「最多 2 轮」= 主链 1 轮 + 修正 1 轮），
  原来按「补跑次数」算会变成 1+2=3 轮，且最后一轮的修正单没人执行，库里多一张会真浇水的孤儿单。

#### bug 3：跑满轮次仍未达标，run 却标 success（run #28）

`result.status = "success"` 是无条件的。run #28 三轮全 failed（40.41%），画布全绿、
报告写「闭环成功」——**数字都在，结论反了**。

修：`_final_status(context)` —— `last_verification` 是 `failed`/`needs_human` 时
落 `needs_human`，`error` 写明「Self-Loop 已用完仍未达标（最后一轮达成率 X%），转人工」。
这是 PRD 11.4 第 3 条的原话。

#### bug 4：修正单时长与真实下发时长不一致（run #29）

修正单载荷写 `duration_s=19.9`，执行管家照着上一轮的「浇水 45 秒」下发，设备真浇了 45 秒。

修：新增 ContextVar `CURRENT_PUMP_DURATION`，`_apply_correction` 里 set，
`_with_executor_device` 在下发时以它为准覆盖 `params.duration_s`。
报告因此才能写出「第 1 轮 45.00s / 第 2 轮 19.90s」并且**物理上真的一样**。

#### 附带：修正单会被建两次（run #29 的 task-0024）

验证层的 `_schedule_correction` 与引擎的 `_apply_correction` 同时开火，
0024（扁平 payload、没 params 包装）派发后一直不 ack、超时重试，时间线多出一串无关事件。

修：`_schedule_correction` 先看 `current_run_id()` —— 工作流在场时不建单（交给引擎），
只有单工具调用 `verify_result` / 脚本手工验证时才兜底建。

## 四、需要 A / B 确认的三点

1. **A（画布）**：Self-Loop 回边现在是 `n11b → n9`（原来是 → n11）。若前端虚线是写死的
   坐标，需要把箭头改成指向「执行浇水」节点；如果读 `dag_json.body_next` 自动画，则不用动。
   库里的 `workflows.dag_json` 我已同步（version+1），`default_dag.py` 也改了。
2. **A（报告页）**：`outcome="needs_human"` 的 run 现在会真的出现（跑满 2 轮仍不达标），
   前端要按「🚨 转人工」渲染，不能当失败重试。
3. **B（设备层）**：`command.send_cmd` 读的是调用方传的 `params.duration_s`，
   不读任务载荷。当前由队长侧在工具调用前覆盖兜底；如果你愿意，可以改成「任务载荷优先，
   调用方参数只作为缺省」—— 这样任何调用方都不会再出现「载荷 19.9、实浇 45」。
