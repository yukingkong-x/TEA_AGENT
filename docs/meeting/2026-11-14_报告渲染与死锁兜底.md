## 一、改了什么

### 1. 报告渲染（对应 B 提的三个洞）

| 洞 | 根因 | 现在 |
| --- | --- | --- |
| 轮次表「浇水时长」恒 0.00s | `verifications` 表没有时长列，时长在被验证任务的 `payload.params.duration_s` | 按 `task_no` 回查任务载荷取值 |
| 轮次号永远「第 1 轮」 | 按验证记录序号排 | 取载荷 `round_no`（Self-Loop 补灌任务带 2），取不到才退序号 |
| 过浇 / 基线已达标提示永不出现 | `achievement_detail` 只塞了目标上下限 | 复测 > 上限 → `over_irrigated`；基线落在区间 → `baseline_in_range` |
| 无验证时结论自相矛盾 + 章节跳号 | outcome 退回 `run.status`（可能是 success）；章节号写死 | 新增 `unverified` 一档文案；章节号按实际输出递增，连号 |

执行时间线改为读 `task_events` 流水（派单 → 接单 → 执行完成，带真实时间戳），不再是「一行 device_cmd 50000ms」。

### 2. run 卡死兜底

run #24 现场：执行管家 13:35:44 下发完，验证官节点再没回来，run 在 `running` 挂了十几分钟，日志里一个字都没有。重启后同一份代码连跑 run #25 正常，**根因没复现**。

已加两道防护：

- 节点进 / 出各一行 `logger.info`（节点 id、名称、状态、耗时），下次卡住直接看停在哪；
- `start_run` 外层 `asyncio.wait_for(RUN_TIMEOUT_S=480s)`，超时写 `failed` 并在 `context_json.error` 注明最后停留节点。**宁可明确失败，也不让 run 永远 running。**

### 3. 测试可移植

容器只挂 `backend/`，仓库根的需求文档不在里面；合并后的仓库里 `devices` 表是真的、`app.seams` 也在。原来三个用例假设「没有基座」，在容器里必红。现在改成显式打瘸依赖（roster 取数抽成 `_query_rows`）、双异常都认（`WorkflowNotReady` / `SeamNotReady`）、PRD 缺席时 skip。
