# 节点耗时落库 + Self-Loop 语义拍板

## 1. 结论：建表，不拿 task_events 近似

我选**建 `workflow_node_records`**，理由是 task_events 顶不了这件事：

1. **task_events 挂在 `task_no` 上**。决策 = none 的巡园轮次、只在 condition 就结束的 run，一条 task_events 都没有 —— 报告时间线会整段空白，而这类 run 恰好是"没浇水"的对照演示。
2. **缺字段**。task_events 只有状态跳变，没有 `duration_ms / tokens / degraded / tool_calls / round`。"哪个 Agent 慢、哪个降级了、哪轮超时"一个都答不上来，而 PRD 9.1 要的是耗时表。
3. **非 agent 节点没有发言**。start / condition / parallel / loop / tool 这些节点在 `agent_messages` 里查不到，但它们占的就是时间线的头尾和那个 90 秒的 `wait_penetration` —— 恰恰是最显眼的耗时块。

成本侧：引擎的 `NodeRecord` 已经把这些字段全攒好了，只是没落库，加一行就够，不改引擎逻辑。

## 3. 队长只需要加这一行

在 `workflow/engine.py` 的 `_drive`（或 `_run`）里，`finally` 中已经算完 `result.duration_ms` 的地方：

```python
finally:
    _clear_current_task(task_token)
    _release_executor_device(device_token)
    result.context = context
    result.duration_ms = int((time.monotonic() - started) * 1000)
    # ↓ 新增这三行
    from app.core import node_records
    await asyncio.to_thread(node_records.record_run_nodes, result.run_id, result.nodes)
    self._fire({...})   # 原有 run_finished
```

放 finally 的原因：节点失败时 `result.nodes` 里也已经写了 `status=failed` / `error`，失败 run 同样要有耗时表（演示"熔断"那条线就靠它）。

`asyncio.to_thread` 是为了不阻塞事件循环（一次事务，10 个节点约 5–10ms，但这台机器上 MySQL 偶发 30ms+）。

**可选替代**：`workflow/wiring.py` 的 `_fire` 回调里处理 `node_finished` 事件 —— 事件字段和表列正好一一对应，能实时写。但每个节点一次事务、并行分支还会并发写，我不推荐，除非你想让报告页在 run 跑的过程中就能看时间线。

### 已知限制（不藏）

引擎的 `by_id` 按 node_id 去重，Self-Loop 重跑同一个 `n11` 时是**同一条 NodeRecord 被覆盖**，所以表里只能记到最后一轮的状态与耗时。要展示「第 1 轮 8.2s / 第 2 轮 6.7s」得让引擎每轮 `append` 一条新 NodeRecord（或给 NodeRecord 加 `round` 字段并在重跑时新建），属于引擎侧改动，我这边按"最后一次"实现。若你决定改，我这边 `_round_of()` 已经优先读 `record.round` / `record.round_no`，改了自动生效。

## 4. Self-Loop 语义：问题不在"先判后循环"

你说 PRD 9.1 的文字和代码没对齐，我查了一遍，**"先判后循环"是对的，不需要改文档；真正对不上的是另外三件事**：

### 4.1 循环体里没有修正动作

`default_dag.py` 的 `n11b.body_next = "n11"`，而 `n11` 是验证官。也就是说循环体 = 「重验」，没有 feedback 节点、没有 executor 节点。

修正任务确实存在，但它在**另一条路径**上：`verification/wiring.py:_schedule_correction()` 在 failed 时建一条 `trigger=selfloop`、`status=pending`、`assigned_device=origin.device_id` 的新任务，由**调度器的定时 tick** 接走派发。它和 DAG 的循环是两条并行线，谁也没等谁。

### 4.2 第二轮的 task_no 还是原任务

`context["last_task_no"]` 只在引擎的 `_ensure_task` 里更新（`engine.py:517/556`），`_schedule_correction` 不回写。所以第 2 轮 `n11` 的验证官拿到的仍是原任务号。

### 4.3 结果会"看起来成功"，但轮次塌了

`verification/wiring.py:_load_samples()` 取的是 `_recent_values(sensor_id, 3)` —— **最近 3 条读数，与任务无关**。所以：

- 第 1 轮 failed（39%）→ 修正任务被调度器派出 → mock 浇水 → 湿度上升到 54%
- 第 2 轮验证**原任务**，但读到的是最新 3 条（含修正后的）→ 达成率 92% → success
- `verifications` 表里同一个 `task_no` 两条记录，`round_no` 都从原任务 payload 读（都是 1）
- 修正任务自己**从来没被验证过**

结论：报告页的"两轮对照"会塌成同一轮的两次结论，时间线上看不到"修正任务被执行"，而演示时它看起来是成功的 —— 这是最危险的一种错。

### 4.4 我的建议（A 为主，B 为备）

**A. 把执行放回循环体（推荐，演示可控）**

```python
{"id": "n11b", "type": "loop", "name": "Self-Loop", "max_iterations": 2,
 "exit_expression": "context.last_verification == 'success' or context.round > 2",
 "body_next": "n9",          # ← 从 n11 改成 n9
 "next": ["n13"]},
```

这样每轮 = 执行管家领单（认领 `pending/dispatched` 且无 `dispatch` 轨迹的最新单，基座已实现）→ 渗透等待 → 验证 → 判。第二轮验的是**修正任务**，`round_no` 天然不同，报告两轮对照成立。

代价：每轮多 45–90 秒（`n10` 的 `wait_penetration`），两轮演示约 4 分钟。建议把 `n10` 的 `seconds` 调到 45。

DAG 校验已确认放行：`api/_dag.py:85` 的环检测**显式忽略 loop 的 body_next 回边**。

**B. 保持循环体只重验，但把轮次归属修好**

`_schedule_correction` 建单后把新任务号写回引擎上下文（比如通过 `_bind_current_task` 旁边加一个可读的 ContextVar，引擎在 `n11b` 判定前取），让第 2 轮验新单。

风险：修正单是调度器异步执行的，第 2 轮验证可能在浇水完成前就跑了 → 结论随机。演示不接受随机。

**我拍板 A。** 文档改法（PRD 9.1 那段）：

> Self-Loop 以 `loop` 节点实现，**先判后循环**：主链的验证结论达标时 `exit_expression` 立即成立，不再进 body（不白跑一轮）；不达标才按 `body_next` 回到执行节点，重新领单 → 渗透等待 → 复测验证 → 再判，`max_iterations` 与 `exit_expression` 里的 `round` 条件双保险。第 2 轮起验证的是验证引擎 `_schedule_correction` 生成的新任务（`trigger=selfloop`，`round_no` 递增），因此报告页能呈现完整两轮对照。

这段的前提是 A 落地。**若你先改文档不改 DAG，等于给 4.3 那个假成功背书** —— 评委只要点开两轮的 verification 记录，看到同一个 task_no、同一个 round，就穿帮了。
