# 硬件模块 · 实际运行手册（队友 C）

> 一句话：传感器走 **PC + USB-RS485 桥接**，继电器走 **无屏幕 K10 执行端**，两者通过 MQTT 联动，前端大屏显示真实数据 + 真浇水闭环。
> 实测记录（踩坑全过程）见 [docs/hardware_log.md](../docs/hardware_log.md)。

---

## 1. 实际架构（与 PRD 原始三板方案不同，以本节为准）

```
气象传感器(0x03) ┐
                ├─ RS485 A/B 并联 ─→ USB-RS485 转换器(COM11) ─→ 电脑桥接脚本
土壤传感器(0x02) ┘                                              │
                                                               │ MQTT(tea / .env 的 MQTT_PASSWORD)
                                                               ↓
                               ┌─────────────────────────────────────────┐
                               │  Mosquitto(Docker, localhost:1883)      │
                               └─────────────────────────────────────────┘
                                        ↓ 遥测              ↓ cmd 指令
                                  后端 → 前端大屏        K10(IO15) → 继电器 → 水泵
                                  (真实数据展示)         (k10-act-03 执行端)
```

**关键差异**（PRD 第 4 章写的是三块板各自上报；实际采用本方案的原因）：
- 实物只有 **一块无屏幕定制 K10**（印字 `LNSF AIoT K10`）+ 两个 RS485 传感器，不是 PRD 的三块板。
- MAX3485 自动方向模块读传感器不稳（读一次就死），最终改用**已验证的 PC USB-RS485 桥接**。
- 那块 K10 专职做**执行终端**（继电器），不再读传感器。

后端按 MQTT **主题第 3 段**识别 device_id，所以桥接脚本发到两个主题即可让前端显示两台设备：
- 气象 → `tea/device/k10-field-01/telemetry`
- 土壤 → `tea/device/esp32-soil-02/telemetry`

## 2. 日常操作（演示必看）

### 2.1 启动传感器桥接（手动）

**双击**：`firmware/tools/启动桥接.bat`

或在终端：
```bash
cd /d "D:\soft program\school\competitive\TEA_AGENT\TEA_AGENT\firmware\tools"
python pc_bridge_tea.py COM11 --interval 10
```

- 会弹出黑窗口，每 10 秒打印一行 `气象=xx℃/xx%/... 土壤=xx%`，**保持窗口开着**（最小化可以）。
- **开机自启已取消**，每次开机需手动双击启动。
- 启动前确认 USB-RS485 转换器插着（CH340，通常是 COM11）。

### 2.2 确认桥接成功（30 秒）

1. **看窗口滚动**：每 10 秒一行、`seq` 递增、有真实数值（不是"读失败"）。刚上电前 1-2 轮读失败属正常，20 秒后稳定。
2. **查后端**：`curl http://localhost:8000/api/sensor/latest`，看 `k10-field-01` 的 `temperature_c` 是真值、`ts` 是当前时间。
3. **看前端**：打开 `http://localhost:5173`，两台设备 online、数值在变。

### 2.3 桥接停了的恢复办法

桥接停的标志：窗口不滚动 / 前端温度卡住不变。

原因几乎都是 **CH340 端口僵死**（拔插 USB 后内核级死锁），恢复步骤：
1. 关掉桥接窗口
2. **拔掉 USB-RS485 的 USB 头 → 等 5 秒 → 插回**
3. 重新双击 `启动桥接.bat`

> 不要试图用别的程序"探测"COM11——打开即关闭会把 CH340 弄僵死，只能物理插拔恢复。

### 2.4 继电器（执行端）掉线恢复

现象：`k10-act-03` 变 offline/suspect、前端灰。

恢复：**拔掉 K10 的 USB → 等 5 秒 → 插回**（物理重启）。十几秒后心跳恢复、变 online。

## 3. 接线速查

### 传感器 → USB-RS485
```
气象传感器：黄线 → A，蓝线 → B
土壤传感器：黄线 → A，蓝线 → B   （并联在同一对 A/B 上）
```
> 若读不到数据，第一排查项就是**对调 A/B**。

### 供电（12V）
```
+12V → 两个传感器 VCC（并联）
GND  → 两个传感器 GND
```
> USB-RS485 自身由 USB 供电，不接 12V。

### K10 → 继电器 → 水泵
```
继电器 VCC → K10 5V
继电器 GND → K10 GND
继电器 IN  → K10 IO15（低电平触发；不要用 GPIO1，定制板会抖动）

水泵侧：充电头红线 → 继电器 COM；继电器 NO → 水泵正极；水泵负极 → 充电头 GND
```
> 水泵用**独立 USB 电源**，不从 K10 取电。当前水泵未接入（COM/NO 空置），控制链路已用继电器咔哒声 + ack 验证通过。

## 4. firmware/ 目录里各工程的实际状态

> 历史上还有 4 个工程（`k10_field` / `esp32_soil` / `k10_rs485` / `k10_diag`）：前两个是早期"三板"方案的板载读数固件（实物无此传感器组合，未投产），后两个是 MAX3485 直读方案的尝试与诊断固件（模块不稳已弃用）。为保持仓库整洁均已移除，完整踩坑记录见 [docs/hardware_log.md](../docs/hardware_log.md)。

| 工程 | 作用 | 状态 |
| --- | --- | --- |
| `k10_act` | **执行终端：IO15 继电器，收 pump 指令回两条 ack** | ✅ **已烧录跑通** |
| `tools/pc_bridge_tea.py` | **USB-RS485 桥接脚本（当前传感器数据来源）** | ✅ **正在使用** |
| `tools/启动桥接.bat` | 双击启动桥接 | ✅ 日常使用 |
| `tools/hw_probe.py` | MQTT 调试探针（sub/pub/cmd） | 备用调试工具 |

### 执行终端 `k10_act` 要点
- 板型必须 `platform=unihiker, board=unihiker_k10`（含 PSRAM），不能用 `esp32-s3-devkitc-1`。
- 无屏幕：已移除 DFRobot_GDL 屏幕代码。
- 继电器脚 `relay_pin=15`（IO15）。
- MQTT 缓冲区 `setBufferSize(768)`，且 publish **必须带 serializeJson 返回的长度**（否则 finished ack 尾部乱码）。
- 烧录端口会变（当前 COM12），**必须确认日志出现 `Chip is ESP32-S3` + MAC 才是真烧进去**。

## 5. 已验证结果（2026-11-18）

- 传感器：气象 23~26℃ / 65~71% / 光照实时刷新；桥接每 10 秒稳定上报。
- 执行端：`pump 6s` → received + finished 两条 ack 齐全，`executed_s=6`；继电器正确吸合/断开。
- 三台设备（field / soil / act）全部 online。
- 端到端：传感器数据 → MQTT → 后端入库 → 前端大屏实时显示，已打通。

## 6. 安全铁律

1. 水泵独立 USB 电源，不从 K10 取电。
2. 继电器触点物理隔离，控制回路与水泵回路分离。
3. 测试在水杯中、垫纸巾；首次通水人在场。
4. 演示中尽量不要拔 USB（一拔就要按 2.3/2.4 恢复）。
